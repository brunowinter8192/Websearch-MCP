# src/scraper/

## Role

URL scraping for the `scrape_url` CLI subcommand and the shared garbage classifier for batch crawling. Turns a single URL into clean, noise-filtered markdown via one stealth crawl4ai browser call (Crawl4AI v0.8.6). Touch this package when changing scrape extraction, cookie/consent handling, or garbage classification. Not the batch crawler itself — that is `src/crawler/`.

**Contract (as of the 2026-08-05 removal of content judgment):** this module reports facts, it does not judge content. `scrape_url_workflow` returns whatever content crawl4ai produced — unconditionally, full length, no status-code gate, no keyword-based rejection — plus the acquisition facts (HTTP status, byte counts, crawl4ai's own anti-bot diagnosis) alongside it. The caller (an agent, with a user to report to) judges; this module used to and no longer does. `is_garbage_content` (automatic verdict) still exists and is still called, but ONLY from `src/crawler/crawl_site.py`'s unattended batch crawl — a different consumer with no agent reviewing its output, where an automatic verdict remains the correct design. Do not reintroduce a call to it from this module's own `try_scrape`/`scrape_url_workflow`.

## Public Interface

`__init__.py` is empty — modules are imported by path:

- `scrape_url_workflow(url)` (scrape_url.py) — imported by `cli.py` as the `scrape_url` subcommand entry. Returns `list[TextContent]`, one item: acquisition facts followed by full content, never truncated.
- `is_garbage_content(content) -> str | None` (scrape_url.py) — imported by `src/crawler/crawl_site.py` for batch-crawl garbage filtering ONLY; not called by this module's own workflow.
- `log_scrape(record)`, `write_sidecar(url, ts, content, outcome, mode)` (scrape_logger.py) — called by scrape_url.py.
- `try_scrape_camoufox(url, block_images=False) -> tuple[str, dict]` (camoufox_scrape.py) — the calibrated acquisition primitive; called by `scrape_url_camoufox_workflow` below, and directly by anyone who wants facts without logging/rendering.
- `scrape_url_camoufox_workflow(url, block_images=False)` (camoufox_scrape.py) — imported by `cli.py` as the `scrape_url_camoufox` subcommand entry, the ad-hoc lane's second acquisition engine (not a fallback of `scrape_url_workflow` — the agent picks one deliberately). Same `list[TextContent]` shape as `scrape_url_workflow`. Pipe-lane wiring is a later milestone.

## Flow

`scrape_url_workflow` → `try_scrape(url)` runs one stealth crawl4ai call → `extract_date` pulls a publication date from the raw HTML (independent of markdown quality) → content selected (fit_markdown if ≥200 chars, else raw_markdown fallback — PruningContentFilter's own fallback, not a garbage check) → result + metadata logged via scrape_logger (JSONL record + content sidecar, full content, no truncation; `landed_url` raw as its own field, no computed verdict alongside it) → `_format_scrape_output` renders acquisition facts (HTTP status, landed URL UNCONDITIONALLY — same treatment as every other fact in the block, whether it matches the requested URL, differs, or is absent — byte counts, crawl4ai's diagnosis labeled as an observation) followed by the full content, always in that order, returned as-is. No code in this module computes or stores a same/different verdict on the two URLs (removed 2026-08, see Gotchas) — an agent reading either the log or the rendered text has both URLs and compares them itself.

## Modules

### scrape_url.py (447 LOC)

**Purpose:** Scrape orchestrator. One crawl4ai browser call with native anti-bot baseline (`enable_stealth` + `UndetectedAdapter` + `magic=True` + `wait_until="load"`, `page_timeout=30000`, `delay_before_return_html=2.0`, `max_retries=0`, no phase escalation) — none of this changed on 2026-08-05. `page_timeout` falls back to 30000 (down from a prior, unmeasured 60000) on the rule "a phase cap is not raised above the default of the layer that executes it without evidence for the raise" — patchright 1.61.2's own `DEFAULT_PLAYWRIGHT_TIMEOUT_IN_MILLISECONDS` is 30000, crawl4ai's CHANGELOG documents its 60000 as an unmeasured raise. `delay_before_return_html=2.0` is explicit (library default 0.1) per crawl4ai issue #1665's third-party saturation-knee measurement (full content by 3s, flat above it); set to 2.0 not 3.0 since `remove_consent_popups`'s own unconditional ~1s wait counts toward the same render window (not additive) — see the CrawlerRunConfig construction comments for the full rationale and sources on both values.

**As of 2026-08-05: no content judgment.** Selects `fit_markdown` (PruningContentFilter 0.48, `preserve_tags=["pre","code"]`) or `raw_markdown` fallback (content SELECTION between two crawl4ai-provided candidates, unchanged) — but no longer classifies, strips, truncates, or discards on that basis. Removed: the `status_code >= 400` early return (real evidence it was wrong: `de.trustpilot.com/review/entega.de` returns HTTP 403 WITH the real 42707-byte review page), the `is_garbage_content` call as a gate (real evidence it was wrong in the OTHER direction too: `idealo.de`'s `OffersOfProduct` page returns HTTP 200 + 401 bytes of "Sorry! Something has gone wrong" and sailed through as a clean `ok`), `strip_consent_prefix`, `truncate_content`/`DEFAULT_MAX_CONTENT_LENGTH`, `_GARBAGE_MESSAGES`, `get_plugin_hint`, `build_config_record`. `scrape_url_workflow` now always returns full content via `_format_scrape_output` (acquisition facts — HTTP status, byte counts, crawl4ai's diagnosis explicitly labeled "an OBSERVATION... NOT a verdict" in the rendered text itself, not just a code comment — followed by the complete content, never truncated). The `except Exception` handler in `try_scrape` distinguishes three ACQUISITION-level failures (meta`["acquisition_error"]`, never a content verdict): a browser-launch/executable-missing failure (`is_browser_launch_error`) → `"browser_missing"`; `asyncio.TimeoutError` on the outer budget → `"budget_exhausted"`; any other exception → `"exception"` (named rather than silently collapsed into the same state as a real empty page, as it was pre-2026-08-05). `try_scrape`'s acquisition (browser launch through content selection, nested in an inner `_acquire()`) runs inside `asyncio.wait_for(TOTAL_SCRAPE_BUDGET_S=39.4)` — the one outer wall-clock guard on this path, since `page_timeout=30000` only bounds Playwright's `page.goto` and everything after a successful goto (crawl4ai's own two internal, non-configurable 30s render waits, consent handling, date extraction, markdown generation) is otherwise unbounded. See Gotchas for two things this guard does NOT cover.

`is_garbage_content` (7 categories, unchanged logic) is STILL exported and still called — but ONLY by `src/crawler/crawl_site.py`'s unattended batch crawl, a categorically different consumer (no agent reviewing its output). `extract_date(html, url)` pulls the original publication date (day-precision ISO) from `result.html` — the raw pre-cleaning HTML crawl4ai captures on every fetch, read here for the first time — via `htmldate.find_date(extensive_search=True, original_date=True)`; runs off the event loop with a 5s hard timeout, any exception/timeout/absence degrades to `None`. Called right after `raw_md` is computed, BEFORE content selection — result stored as `meta["date"]`. Rendered as an optional `Published: <date>` line between the `# Content from:` header and the acquisition-facts block. `extract_crawl4ai_diagnosis(result)` reads crawl4ai's own anti-bot verdict off the result object (`success`, `error_message`, `crawl_stats["attempts"|"resolved_by"|"fallback_fetch_used"]`) — an OBSERVATION, surfaced to BOTH the scrape log AND (as of 2026-08-05) `_format_scrape_output`'s rendered text, never consulted by this module's own return value. `extract_config_stamp(browser_config, adapter, crawler_strategy, run_config)` reads the scrape-governing kwargs back off the just-constructed config objects (never re-declares their values); also folds in `min_content_threshold` (module constant, same "read the real value" treatment as `total_budget_s`) directly — `build_config_record` is gone, its only job (merging the now-removed `max_content_length`) disappeared with it. `hash_config(config)` derives a 10-hex-char sha256 grouping key — `config_hash` changed shape on 2026-08-05 (no more `max_content_length`), so it does not group with pre-change records even under an otherwise-similar config.
**`landed_url` (no comparison function — removed, see Gotchas):** `_acquire()` reads `meta["landed_url"] = getattr(result, "redirected_url", None)` RAW (never normalized) right where `status_code`/`content_type` are read, so it's present even on the zero-markdown early return; `None` on every path that never obtains a result object (`_empty_meta` carries `"landed_url": None`, spread into the `budget_exhausted`/`browser_missing`/`exception` returns). `scrape_url_workflow` logs `landed_url` (raw) as its own JSONL field — no verdict computed or stored alongside it. `_format_scrape_output` renders a `- Landed URL (the URL the browser actually returned content from): <url>` line UNCONDITIONALLY, placed right after the HTTP-status line (a 301 next to it is then self-explanatory — no second status field added), on every scrape — matching (equal to the requested URL), differing, or absent (`None`, rendered literally like every other absent value in this block) all render the same way; nothing decides which of these the agent gets to see.
`status_code` is the FIRST hop of a redirect chain while `landed_url`/content are the LAST (crawl4ai's own behavior, `async_crawler_strategy.py`) — a record can legitimately show `http_status: 301` next to real, full content; this is not a bug and is NOT given a second status field, by design.
`scrape_url_workflow`'s `log_scrape` call now also stamps `"engine": "chromium"` — a first-class discriminator against `camoufox_scrape.py`'s `"engine": "camoufox"` records sharing this same `scrape_log.jsonl` file (the config stamp shape already differs, but a reader shouldn't have to infer engine from it). Retrofitted onto this existing call so the field is symmetric across both lanes, not one-sided.
**Reads:** `url` arg (no other parameters — `max_content_length` removed 2026-08-05).
**Writes:** result content + metadata via scrape_logger (no direct file writes).
**Called by:** `cli.py` (scrape_url_workflow); `src/crawler/crawl_site.py` (is_garbage_content); `src/crawler/pipe_scraper.py` (hash_config, extract_crawl4ai_diagnosis — reused as-is, not path-specific).
**Calls out:** `crawl4ai` (AsyncWebCrawler, BrowserConfig, CrawlerRunConfig, CacheMode, UndetectedAdapter, AsyncPlaywrightCrawlerStrategy, PruningContentFilter, DefaultMarkdownGenerator); `htmldate` (find_date); `mcp.types.TextContent`; `scrape_logger` (log_scrape, write_sidecar).

### scrape_logger.py (191 LOC)

**Purpose:** Per-URL structured logging for scrape_url. Two outputs per call: one JSONL record appended to the scrape log, one sidecar `.md` holding the exact content the caller received (as of 2026-08-05: ALWAYS the full, real content — no more "garbage_content" special case, since nothing is classified as garbage here anymore). No sidecar on empty outcome. JSONL record carries `published_date` (htmldate-extracted, `"ok"` outcome only); the sidecar header does NOT — the date is already visible in both the returned content and the JSONL log, a third copy was judged redundant. JSONL record also carries crawl4ai's own anti-bot diagnosis verbatim (`crawl4ai_success`, `crawl4ai_error_message`, `crawl4ai_attempts`, `crawl4ai_resolved_by`, `crawl4ai_fallback_fetch_used`, all `null` when no result was ever obtained) — an OBSERVATION, recorded for later analysis AND (as of 2026-08-05) surfaced to the caller too, never fed back into any verdict of this project's own (crawl4ai's block detector has documented false positives — e.g. reports "Cloudflare JS challenge" on guenstiger.de even when the full product page came back). `outcome` (`ok`/`empty`/`budget_exhausted`/`browser_missing`/`exception`) as of 2026-08-05 no longer includes content-judgment categories (`http_error`/`cookie_wall`/`login_wall`/`cloudflare`/`nav_dump`/`minimal_content`/`crawl4ai_error`) — those are HISTORICAL-ONLY values on records written before that date, named explicitly in the schema comment so an aggregate spanning the boundary reads correctly (the classifier that emitted them was removed, not evidence those failure modes stopped happening). Same historical-only treatment for the now-dropped `garbage_type`/`truncated`/`consent_stripped` fields — present on old records, absent by design (not a bug) on every new one. JSONL record also carries `landed_url` (str|null, crawl4ai's `result.redirected_url` verbatim, RAW/unnormalized — the reverse historical case: ABSENT on records written before this field was added, present from then onward). No verdict is stored alongside it: an earlier design (`same_target`, `is_same_target(url, landed_url)` computed at write time) was added and then REMOVED — see Gotchas for why; `same_target` is now a narrow-window historical field (absent / present / absent again), not an ongoing one. JSONL record also carries a `config`/`config_hash` stamp of the scrape config in effect for that call (see scrape_url.py's `extract_config_stamp`/`hash_config`) — adds ~450 bytes/record; deliberate given this is a slow-growing log (~160 records/2 weeks of real use pre-2026-08-05), not a high-volume stream, and the whole point is comparing outcomes across config changes over weeks of accumulation.

**Shared by TWO acquisition lanes as of camoufox_scrape.py's ad-hoc CLI wiring** (`scrape_url.py`'s crawl4ai/chromium path AND `camoufox_scrape.py`'s Camoufox/Firefox path both call this same `log_scrape`/`write_sidecar`). `"engine"` (`"chromium"` | `"camoufox"`) is the first-class discriminator — absent on records predating the field. Every field that only ONE lane's acquisition can produce is documented as ABSENT (key never written), not null, on the other lane's records — `content_type`/`fallback_to_raw`/`crawl4ai_success`/`crawl4ai_error_message`/`crawl4ai_attempts`/`crawl4ai_resolved_by`/`crawl4ai_fallback_fetch_used`/`published_date` (chromium-only: htmldate extraction never runs on the camoufox lane, a permanent engine characteristic, not a per-call miss) vs `markdown_conversion_error`/`content_is_raw_html` (camoufox-only: crawl4ai's raw:// markdown-conversion diagnosis, no equivalent concept on the chromium lane, which extracts markdown directly from its own live crawl4ai result). `landed_url`/`config`/`config_hash` are the fields BOTH lanes populate — `config`'s actual KEY SET differs completely by engine (chromium: `headless`/`enable_stealth`/`adapter`/... vs camoufox: `headless`/`os`/`block_images`/`executable_path`/...), which is exactly the shape-difference `"engine"` exists so a reader doesn't have to detect manually. `"mode"` also gained two camoufox-only values (`"markdown"`/`"raw_html"`, describing which kind of content is actually in the sidecar) alongside the chromium lane's fixed `"filtered"`.
**Reads:** `WEBSEARCH_SCRAPE_LOG_PATH` env var (fallback `src/logs/scrape_log.jsonl`); sidecar dir `<log_dir>/scrape_content/`.
**Writes:** `src/logs/scrape_log.jsonl` (one line per call); `<log_dir>/scrape_content/<ts>_<slug>.md` (per-call sidecar). Both gitignored.
**Called by:** `scrape_url.py` (end of scrape_url_workflow); `camoufox_scrape.py` (end of scrape_url_camoufox_workflow) — same log file, both lanes, see the engine-discriminator note above.
**Calls out:** `src/log_janitor.py` (maybe_prune_jsonl, maybe_prune_sidecars).

### camoufox_scrape.py (457 LOC)

**Purpose:** Calibrated core acquisition module for the Camoufox lane — a SECOND, parallel acquisition path beside scrape_url.py's crawl4ai/chromium path, not a fallback (no trigger logic anywhere). `try_scrape_camoufox(url, block_images=False) -> (content, meta)` launches one headed Camoufox (Playwright-Firefox, C++-level fingerprint spoofing) browser, navigates, captures HTML + landed URL + status, then converts HTML to markdown via crawl4ai's own `raw://` pipeline (reused exactly as `pipe_scraper._own_fallback_rescue` does — no hand-rolled HTML-to-markdown, no new library). No content judgment, same fact-reporting contract as the rest of the scrape surface. `TOTAL_CAMOUFOX_BUDGET_S=61.1` (30.0 Camoufox browser launch + 30.0 `page.goto`, both Playwright's own unmodified defaults, no Camoufox-specific evidence to depart from them — plus 1.1 markdown-conversion browser cold start, reused from scrape_url.py's own measured chromium/patchright figure) is the one outer wall-clock guard, same pattern as `TOTAL_SCRAPE_BUDGET_S`.

Calibration surface (`_build_camoufox_kwargs`, every value justified in its own comment): `headless=False` (fixed, visible window accepted — headless is the most-detected posture per field evidence), `os="macos"` (fixed to the REAL host OS, not Camoufox's own random windows/macos/linux choice — headed mode's screen size derives from the real monitor regardless of spoofed OS, so matching the real host avoids an internal fingerprint mismatch), `block_webgl` NOT set (fixed — GPU/WebGL stays on, same posture as scrape_url.py's `enable_stealth`), `humanize`/`geoip`/`enable_cache`/`locale` all deliberately LEFT UNSET (each independently justified — `humanize`: no mouse-driven interaction in this flow to benefit from it; `geoip`: reverses the earlier probe after reading `camoufox/ip.py` — without a proxy it triggers a real, previously-invisible network round-trip up to 30s worst case against 6 third-party IP-echo services, for an unverified benefit since geoip's documented core value is proxy-IP matching and this project has no proxy; `enable_cache`: no multi-page benefit for a one-shot fetch, costs memory Camoufox is already field-reported as heavier on; `locale`: no target IP to match without geoip), `block_images` is the one PARAMETERIZED (per-lane) knob. Every other launch parameter (fonts, addons, screen, window, fingerprint_preset, ff_version, main_world_eval, disable_coop, block_webrtc, webgl_config, firefox_user_prefs, `config`) is left at its library default under one blanket rule: BrowserForge's defaults mimic the real statistical distribution of device characteristics; hand-setting any without a measured reason reintroduces the exact fingerprint inconsistency the stealth doc warns gets Camoufox detected. `config` specifically must NEVER be hand-populated (Camoufox's own docs).

`_extract_camoufox_config_stamp(kwargs, resolved)` reads `executable_path` off the REAL resolved `launch_options()` output but DELIBERATELY excludes the rest of that resolved dict (fingerprint config, seeds, env vars) — those are randomized PER LAUNCH by BrowserForge design, so hashing them would make `config_hash` unique on every call and defeat its purpose as a "same config" grouping key. `launch_options()` is called ONCE by this module itself (not left to `AsyncCamoufox`'s own internal call) and handed back via `from_options=` specifically to avoid generating a SECOND, different random fingerprint just for the stamp.

**Markdown-conversion failure is a visible FACT, not a silent content loss:** a real run against `idealo.de` found crawl4ai's OWN internal `urlparse()` call on the `raw://<html>` pseudo-URL raises `Invalid IPv6 URL` whenever the HTML contains a bare `[` before the first `/` in the document (e.g. an early inline `<script>` with a JS array literal) — crawl4ai swallows this internally (`success=False`, `markdown=None`) rather than raising. `meta["markdown_conversion_error"]` (str|None, an OBSERVATION, crawl4ai's verbatim message) and `meta["content_is_raw_html"]` (bool, explicit format flag, not inferred from the error field) surface this: when conversion fails, `content` is the RAW CAPTURED HTML (never silently discarded as `""`) rather than empty. Deliberately NOT folded into `acquisition_error` — that field means "no result at all," which is false here (real HTML, status, landed_url all present); this is a downstream conversion failure, a categorically different state. Pre-existing crawl4ai bug, not fixed here (no crawl4ai patch, no hand-rolled markdown, out of scope) — see Gotchas for its blast radius on `pipe_scraper.py`.

**`scrape_url_camoufox_workflow(url, block_images=False)`** (ad-hoc CLI wiring, mirrors `scrape_url_workflow` exactly): calls `try_scrape_camoufox`, logs one record to the SAME `scrape_log.jsonl` via the SAME `log_scrape`/`write_sidecar` scrape_url.py's lane uses (`"engine": "camoufox"` is the discriminator — see scrape_logger.py's entry), renders via `_format_camoufox_output`. `config_hash` is read straight off `meta["config_hash"]` (computed ONCE, inside `try_scrape_camoufox` itself) — NOT re-hashed here, unlike the chromium lane where the workflow computes it; the two lanes differ on WHERE the hash is computed, deliberately, to avoid double-hashing given `try_scrape_camoufox` already needs it for its own return value. `"mode"` reuses the EXISTING scrape_logger.py field for its own documented purpose (describing sidecar/log content kind) rather than inventing a new one: `"markdown"` normally, `"raw_html"` when `content_is_raw_html` is set.

**`_format_camoufox_output(url, content, meta)`**: a SIBLING to `scrape_url.py`'s `_format_scrape_output`, not a shared function — same fixed-shape philosophy (facts always, unconditionally, before a fixed `## Content` delimiter; landed URL unconditional, same rule as the chromium lane) applied to THIS lane's own, genuinely different fact vocabulary (no `content_type`, no crawl4ai diagnosis, no `fallback_to_raw`; has `markdown_conversion_error`/`content_is_raw_html` which the chromium lane has no concept of at all). Sharing one renderer would have required conditional logic that itself violates "always the same shape." The `content_is_raw_html` line is present only when true (same conditional-presence precedent as the `Acquisition error` line) but worded PLAINLY when it appears — the agent must know unambiguously that it is reading raw HTML, not markdown, and why (crawl4ai's `markdown_conversion_error` surfaced verbatim as an OBSERVATION).

**No-focus-steal launch — RESOLVED, benefits both lanes:** `_ensure_no_focus_steal(executable_path)` (called once per `_acquire()`, idempotent) sets `LSUIElement=true` on the resolved Camoufox `.app` bundle's `Info.plist`. The chrome lane's own mechanism (`open -g`, `src/search/browser.py`) has NO equivalent here — Playwright launches the browser from inside its own internal Node.js driver, exposing no `process_creator`-style hook to substitute a custom launcher. `LSUIElement` is a DIFFERENT lever that works anyway: a property of the app bundle itself (Camoufox's fetched build IS a real macOS `.app`, verified via `launch_path()`), read by macOS at `NSApplication` startup independent of how the process was spawned. Verified empirically, not assumed: a real `osascript`/System Events focus-poll around a live `try_scrape_camoufox` call showed "camoufox" becoming frontmost for ~1.2s of a 1.8s run WITHOUT the fix, and the calling terminal staying frontmost for the ENTIRE run WITH it — reproduced again under a real 4-URL pipe batch run (46/46 poll samples, terminal frontmost throughout). Firefox timer/render throttling in an unfocused window — the other half of this concern — is ALREADY handled by Camoufox's own shipped `camoufox.cfg`: `focusmanager.testmode=true`, with the comment "Allow the application to have focus even it runs in the background" — found directly in the installed config, not guessed.

**Reads:** `url` arg, `block_images` arg.
**Writes:** `scrape_log.jsonl` + sidecar via scrape_logger.py (as of the ad-hoc CLI wiring — `try_scrape_camoufox` itself still writes nothing, only `scrape_url_camoufox_workflow` does).
**Called by:** `cli.py` (`scrape_url_camoufox` subcommand → `scrape_url_camoufox_workflow`). Pipe-lane wiring is a later milestone.
**Calls out:** `camoufox` (launch_options, AsyncCamoufox, CamoufoxNotInstalled); `crawl4ai` (AsyncWebCrawler, BrowserConfig, CrawlerRunConfig, CacheMode, DefaultMarkdownGenerator) for the markdown-conversion step only; `src.scraper.scrape_url` (hash_config); `src.scraper.scrape_logger` (log_scrape, write_sidecar); `mcp.types.TextContent`.

## State

No shared in-memory state — each `scrape_url_workflow` call is independent. The only persistence is the JSONL log + content sidecars written by scrape_logger and pruned by log_janitor.

## Gotchas

- `TOTAL_SCRAPE_BUDGET_S=39.4` (`scrape_url.py`) is the only outer wall-clock guard on this path — `page_timeout=30000` bounds only `page.goto`; `delay_before_return_html=2.0` bounds only the render wait before HTML capture. Two things the outer guard does NOT cover: (1) `asyncio.wait_for` cancels only at await points — markdown generation + `PruningContentFilter` run as synchronous CPU inside crawl4ai's `arun()`, so a pathological synchronous parse can overrun the budget before the guard gets a chance to fire; not fixed (no thread offload/executor), documented as a known limit. (2) The guarded span is ACQUISITION only (`_acquire()`: browser call + date extraction + content selection) — post-acquisition local work (`write_sidecar`, `log_scrape`, output formatting) runs outside it so a budget-exhausted record stays writable; `timings_ms.total_wall` in the log can therefore exceed 39.4s by that post-processing cost.
- `remove_overlay_elements` is NOT used — it misclassifies legitimate DOM (e.g. Wikipedia content) as overlays and destroys content. Cookie removal is done via `excluded_selector=COOKIE_CONSENT_SELECTOR` instead.
- `cky-modal` MUST stay in `COOKIE_CONSENT_SELECTOR` — CookieYes stores the full 12K+ char consent dialog there; without it only the 236-char banner is stripped.
- **As of 2026-08-05, `is_garbage_content` is NOT called by this module's own `try_scrape`/`scrape_url_workflow`.** Do not reintroduce that call — the whole point of the change was that content judgment moved to the caller (an agent). The function still exists, unchanged (7 categories: `minimal_content`, `crawl4ai_error`, `http_error`, `nav_dump`, `cookie_wall`, `login_wall`, `cloudflare`), exported ONLY for `src/crawler/crawl_site.py`'s unattended batch-crawl filter — a different consumer, correctly still automatic. A regression test (`tests/test_scrape_url.py::test_try_scrape_does_not_call_is_garbage_content`) guards against this being called from `try_scrape` again.
- `fit_markdown < 200` chars (`MIN_CONTENT_THRESHOLD`) triggers `raw_markdown` fallback — table-heavy pages filter to near-empty otherwise. This is content SELECTION between two crawl4ai-provided candidates (unchanged by the 2026-08-05 removal), not a garbage/quality verdict — see `meta["fallback_to_raw"]`.
- **`http_status` is a fact, not a verdict, as of 2026-08-05** — a status code no longer gates content on its own. Real evidence both directions: `de.trustpilot.com/review/entega.de` returns HTTP 403 WITH the real 42707-byte review page (a status>=400 gate would have discarded all of it); `idealo.de`'s `OffersOfProduct` page returns HTTP 200 with 401 bytes of "Sorry! Something has gone wrong" (a content classifier let it through as clean).
- **`landed_url` identical to the requested URL does NOT prove no redirect happened.** Real CLI run against `idealo.de`'s `OffersOfProduct` page came back with `landed_url` IDENTICAL to the requested URL, HTTP 200, the 367-byte "Sorry! Something has gone wrong" block page. The most plausible reading is that the block page is served directly at the requested URL with no browser-level redirect at all, but a redirect BACK to the same URL is equally consistent with this same observation and cannot be distinguished from it using `landed_url` alone — recorded as a candidate explanation, not a settled mechanism. Do not read a matching `landed_url` next to a thin/blocked-looking page as proof the URL was never redirected.
- **No comparison function exists in this module anymore, and no verdict is stored in the log or rendered conditionally.** `is_same_target` (the requested-vs-landed comparison primitive) and the `same_target` field it fed were both ADDED then REMOVED within the same body of work (`process-docs/scrape_pipeline/`, the `landed_url_*` entries) — not a partial rollback, a deliberate reversal after review: the log is read only by an agent, after the fact, with both `url` and `landed_url` already in the same record, so a stored verdict was a re-derivable conclusion kept as data; the conditional render in `_format_scrape_output` was the one place this module decided which facts the agent gets to see, which is the exact contract the 2026-08-05 removal inverted.
