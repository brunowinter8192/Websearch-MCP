# src/scraper/

## Role

URL scraping for the `scrape_url` CLI subcommand and the shared garbage classifier for batch crawling. Turns a single URL into clean, noise-filtered markdown via one stealth crawl4ai browser call (Crawl4AI v0.8.6). Touch this package when changing scrape extraction, cookie/consent handling, or garbage classification. Not the batch crawler itself — that is `src/crawler/`.

**Contract (as of the 2026-08-05 removal of content judgment):** this module reports facts, it does not judge content. `scrape_url_workflow` returns whatever content crawl4ai produced — unconditionally, full length, no status-code gate, no keyword-based rejection — plus the acquisition facts (HTTP status, byte counts, crawl4ai's own anti-bot diagnosis) alongside it. The caller (an agent, with a user to report to) judges; this module used to and no longer does. `is_garbage_content` (automatic verdict) still exists and is still called, but ONLY from `src/crawler/crawl_site.py`'s unattended batch crawl — a different consumer with no agent reviewing its output, where an automatic verdict remains the correct design. Do not reintroduce a call to it from this module's own `try_scrape`/`scrape_url_workflow`.

## Public Interface

`__init__.py` is empty — modules are imported by path:

- `scrape_url_workflow(url)` (scrape_url.py) — imported by `cli.py` as the `scrape_url` subcommand entry. Returns `list[TextContent]`, one item: acquisition facts followed by full content, never truncated.
- `is_garbage_content(content) -> str | None` (scrape_url.py) — imported by `src/crawler/crawl_site.py` for batch-crawl garbage filtering ONLY; not called by this module's own workflow.
- `log_scrape(record)`, `write_sidecar(url, ts, content, outcome, mode)` (scrape_logger.py) — called by scrape_url.py.

## Flow

`scrape_url_workflow` → `try_scrape(url)` runs one stealth crawl4ai call → `extract_date` pulls a publication date from the raw HTML (independent of markdown quality) → content selected (fit_markdown if ≥200 chars, else raw_markdown fallback — PruningContentFilter's own fallback, not a garbage check) → `is_same_target(url, meta["landed_url"])` compares requested vs. landed URL → result + metadata logged via scrape_logger (JSONL record + content sidecar, full content, no truncation; `landed_url` raw + `same_target` verdict as their own fields) → `_format_scrape_output` renders acquisition facts (HTTP status, landed URL ONLY on a real deviation, byte counts, crawl4ai's diagnosis labeled as an observation) followed by the full content, always in that order, returned as-is.

## Modules

### scrape_url.py (514 LOC)

**Purpose:** Scrape orchestrator. One crawl4ai browser call with native anti-bot baseline (`enable_stealth` + `UndetectedAdapter` + `magic=True` + `wait_until="load"`, `page_timeout=30000`, `delay_before_return_html=2.0`, `max_retries=0`, no phase escalation) — none of this changed on 2026-08-05. `page_timeout` falls back to 30000 (down from a prior, unmeasured 60000) on the rule "a phase cap is not raised above the default of the layer that executes it without evidence for the raise" — patchright 1.61.2's own `DEFAULT_PLAYWRIGHT_TIMEOUT_IN_MILLISECONDS` is 30000, crawl4ai's CHANGELOG documents its 60000 as an unmeasured raise. `delay_before_return_html=2.0` is explicit (library default 0.1) per crawl4ai issue #1665's third-party saturation-knee measurement (full content by 3s, flat above it); set to 2.0 not 3.0 since `remove_consent_popups`'s own unconditional ~1s wait counts toward the same render window (not additive) — see the CrawlerRunConfig construction comments for the full rationale and sources on both values.

**As of 2026-08-05: no content judgment.** Selects `fit_markdown` (PruningContentFilter 0.48, `preserve_tags=["pre","code"]`) or `raw_markdown` fallback (content SELECTION between two crawl4ai-provided candidates, unchanged) — but no longer classifies, strips, truncates, or discards on that basis. Removed: the `status_code >= 400` early return (real evidence it was wrong: `de.trustpilot.com/review/entega.de` returns HTTP 403 WITH the real 42707-byte review page), the `is_garbage_content` call as a gate (real evidence it was wrong in the OTHER direction too: `idealo.de`'s `OffersOfProduct` page returns HTTP 200 + 401 bytes of "Sorry! Something has gone wrong" and sailed through as a clean `ok`), `strip_consent_prefix`, `truncate_content`/`DEFAULT_MAX_CONTENT_LENGTH`, `_GARBAGE_MESSAGES`, `get_plugin_hint`, `build_config_record`. `scrape_url_workflow` now always returns full content via `_format_scrape_output` (acquisition facts — HTTP status, byte counts, crawl4ai's diagnosis explicitly labeled "an OBSERVATION... NOT a verdict" in the rendered text itself, not just a code comment — followed by the complete content, never truncated). The `except Exception` handler in `try_scrape` distinguishes three ACQUISITION-level failures (meta`["acquisition_error"]`, never a content verdict): a browser-launch/executable-missing failure (`is_browser_launch_error`) → `"browser_missing"`; `asyncio.TimeoutError` on the outer budget → `"budget_exhausted"`; any other exception → `"exception"` (named rather than silently collapsed into the same state as a real empty page, as it was pre-2026-08-05). `try_scrape`'s acquisition (browser launch through content selection, nested in an inner `_acquire()`) runs inside `asyncio.wait_for(TOTAL_SCRAPE_BUDGET_S=39.4)` — the one outer wall-clock guard on this path, since `page_timeout=30000` only bounds Playwright's `page.goto` and everything after a successful goto (crawl4ai's own two internal, non-configurable 30s render waits, consent handling, date extraction, markdown generation) is otherwise unbounded. See Gotchas for two things this guard does NOT cover.

`is_garbage_content` (7 categories, unchanged logic) is STILL exported and still called — but ONLY by `src/crawler/crawl_site.py`'s unattended batch crawl, a categorically different consumer (no agent reviewing its output). `extract_date(html, url)` pulls the original publication date (day-precision ISO) from `result.html` — the raw pre-cleaning HTML crawl4ai captures on every fetch, read here for the first time — via `htmldate.find_date(extensive_search=True, original_date=True)`; runs off the event loop with a 5s hard timeout, any exception/timeout/absence degrades to `None`. Called right after `raw_md` is computed, BEFORE content selection — result stored as `meta["date"]`. Rendered as an optional `Published: <date>` line between the `# Content from:` header and the acquisition-facts block. `extract_crawl4ai_diagnosis(result)` reads crawl4ai's own anti-bot verdict off the result object (`success`, `error_message`, `crawl_stats["attempts"|"resolved_by"|"fallback_fetch_used"]`) — an OBSERVATION, surfaced to BOTH the scrape log AND (as of 2026-08-05) `_format_scrape_output`'s rendered text, never consulted by this module's own return value. `extract_config_stamp(browser_config, adapter, crawler_strategy, run_config)` reads the scrape-governing kwargs back off the just-constructed config objects (never re-declares their values); also folds in `min_content_threshold` (module constant, same "read the real value" treatment as `total_budget_s`) directly — `build_config_record` is gone, its only job (merging the now-removed `max_content_length`) disappeared with it. `hash_config(config)` derives a 10-hex-char sha256 grouping key — `config_hash` changed shape on 2026-08-05 (no more `max_content_length`), so it does not group with pre-change records even under an otherwise-similar config.
**`is_same_target(requested_url, landed_url) -> bool`**: does the requested URL and the URL a browser actually landed on point at the same target? Treats scheme/host case, a leading `www.`, the scheme's own default port, empty-path-vs-`/`, a trailing slash, the fragment, and http-vs-https as mere spelling (never reported); treats any other host/path difference and ANY query-string difference (deliberately including tracking-parameter-shaped ones — no allowlist, since a query param often DOES determine content) as a genuinely different target. RFC 3986 §6.2.2.2 percent-encoding normalization is implemented (decode unreserved octets, uppercase remaining hex); dot-segment resolution is not (no observed case needs it). Either URL `None`/empty → `True` (no fact to report from an absence — an expected shape, e.g. crawl4ai leaves the landed URL unset on some paths). Either URL unparseable (bad port, malformed IPv6 literal) → `False`, and NEVER raises — `urlparse()`/`.port`/`.hostname` can raise `ValueError` lazily or inline depending on Python version, all caught, since a later caller runs this from inside `try_scrape`'s guarded span AFTER content was already fetched and must not turn a successful scrape into a failure over an annotation. **Wired in:** `_acquire()` reads `meta["landed_url"] = getattr(result, "redirected_url", None)` RAW (never normalized — that normalization is `is_same_target`'s comparison rule, not a storage format) right where `status_code`/`content_type` are read, so it's present even on the zero-markdown early return; `None` on every path that never obtains a result object (`_empty_meta` carries `"landed_url": None`, spread into the `budget_exhausted`/`browser_missing`/`exception` returns). `scrape_url_workflow` logs both `landed_url` (raw) and `same_target` (`is_same_target(url, meta["landed_url"])`, evaluated at write time) as their own JSONL fields. `_format_scrape_output` renders a `- Landed URL (redirected to a different target than requested): <url>` line, placed right after the HTTP-status line (a 301 next to it is then self-explanatory — no second status field added), ONLY when `landed_url` is truthy AND `is_same_target` says it differs; absent on the ordinary no-redirect case and on mere-spelling differences.
`status_code` is the FIRST hop of a redirect chain while `landed_url`/content are the LAST (crawl4ai's own behavior, `async_crawler_strategy.py`) — a record can legitimately show `http_status: 301` next to real, full content; this is not a bug and is NOT given a second status field, by design.
**Reads:** `url` arg (no other parameters — `max_content_length` removed 2026-08-05).
**Writes:** result content + metadata via scrape_logger (no direct file writes).
**Called by:** `cli.py` (scrape_url_workflow); `src/crawler/crawl_site.py` (is_garbage_content); `src/crawler/pipe_scraper.py` (hash_config, extract_crawl4ai_diagnosis — reused as-is, not path-specific).
**Calls out:** `crawl4ai` (AsyncWebCrawler, BrowserConfig, CrawlerRunConfig, CacheMode, UndetectedAdapter, AsyncPlaywrightCrawlerStrategy, PruningContentFilter, DefaultMarkdownGenerator); `htmldate` (find_date); `mcp.types.TextContent`; `scrape_logger` (log_scrape, write_sidecar).

### scrape_logger.py (116 LOC)

**Purpose:** Per-URL structured logging for scrape_url. Two outputs per call: one JSONL record appended to the scrape log, one sidecar `.md` holding the exact content the caller received (as of 2026-08-05: ALWAYS the full, real content — no more "garbage_content" special case, since nothing is classified as garbage here anymore). No sidecar on empty outcome. JSONL record carries `published_date` (htmldate-extracted, `"ok"` outcome only); the sidecar header does NOT — the date is already visible in both the returned content and the JSONL log, a third copy was judged redundant. JSONL record also carries crawl4ai's own anti-bot diagnosis verbatim (`crawl4ai_success`, `crawl4ai_error_message`, `crawl4ai_attempts`, `crawl4ai_resolved_by`, `crawl4ai_fallback_fetch_used`, all `null` when no result was ever obtained) — an OBSERVATION, recorded for later analysis AND (as of 2026-08-05) surfaced to the caller too, never fed back into any verdict of this project's own (crawl4ai's block detector has documented false positives — e.g. reports "Cloudflare JS challenge" on guenstiger.de even when the full product page came back). `outcome` (`ok`/`empty`/`budget_exhausted`/`browser_missing`/`exception`) as of 2026-08-05 no longer includes content-judgment categories (`http_error`/`cookie_wall`/`login_wall`/`cloudflare`/`nav_dump`/`minimal_content`/`crawl4ai_error`) — those are HISTORICAL-ONLY values on records written before that date, named explicitly in the schema comment so an aggregate spanning the boundary reads correctly (the classifier that emitted them was removed, not evidence those failure modes stopped happening). Same historical-only treatment for the now-dropped `garbage_type`/`truncated`/`consent_stripped` fields — present on old records, absent by design (not a bug) on every new one. JSONL record also carries `landed_url` (str|null, crawl4ai's `result.redirected_url` verbatim, RAW/unnormalized — the reverse historical case: ABSENT on records written before this field was added, present from then onward) and `same_target` (bool, `scrape_url.py`'s `is_same_target(url, landed_url)` evaluated AT WRITE TIME under this project's same/different rule — stored so that decision stays visible even if the rule is later revised; re-derive from `url`+`landed_url` rather than assuming an old record's stored verdict still matches a new rule). JSONL record also carries a `config`/`config_hash` stamp of the scrape config in effect for that call (see scrape_url.py's `extract_config_stamp`/`hash_config`) — adds ~450 bytes/record; deliberate given this is a slow-growing log (~160 records/2 weeks of real use pre-2026-08-05), not a high-volume stream, and the whole point is comparing outcomes across config changes over weeks of accumulation.
**Reads:** `WEBSEARCH_SCRAPE_LOG_PATH` env var (fallback `src/logs/scrape_log.jsonl`); sidecar dir `<log_dir>/scrape_content/`.
**Writes:** `src/logs/scrape_log.jsonl` (one line per call); `<log_dir>/scrape_content/<ts>_<slug>.md` (per-call sidecar). Both gitignored.
**Called by:** `scrape_url.py` (end of scrape_url_workflow).
**Calls out:** `src/log_janitor.py` (maybe_prune_jsonl, maybe_prune_sidecars).

## State

No shared in-memory state — each `scrape_url_workflow` call is independent. The only persistence is the JSONL log + content sidecars written by scrape_logger and pruned by log_janitor.

## Gotchas

- `TOTAL_SCRAPE_BUDGET_S=39.4` (`scrape_url.py`) is the only outer wall-clock guard on this path — `page_timeout=30000` bounds only `page.goto`; `delay_before_return_html=2.0` bounds only the render wait before HTML capture. Two things the outer guard does NOT cover: (1) `asyncio.wait_for` cancels only at await points — markdown generation + `PruningContentFilter` run as synchronous CPU inside crawl4ai's `arun()`, so a pathological synchronous parse can overrun the budget before the guard gets a chance to fire; not fixed (no thread offload/executor), documented as a known limit. (2) The guarded span is ACQUISITION only (`_acquire()`: browser call + date extraction + content selection) — post-acquisition local work (`write_sidecar`, `log_scrape`, output formatting) runs outside it so a budget-exhausted record stays writable; `timings_ms.total_wall` in the log can therefore exceed 39.4s by that post-processing cost.
- `remove_overlay_elements` is NOT used — it misclassifies legitimate DOM (e.g. Wikipedia content) as overlays and destroys content. Cookie removal is done via `excluded_selector=COOKIE_CONSENT_SELECTOR` instead.
- `cky-modal` MUST stay in `COOKIE_CONSENT_SELECTOR` — CookieYes stores the full 12K+ char consent dialog there; without it only the 236-char banner is stripped.
- **As of 2026-08-05, `is_garbage_content` is NOT called by this module's own `try_scrape`/`scrape_url_workflow`.** Do not reintroduce that call — the whole point of the change was that content judgment moved to the caller (an agent). The function still exists, unchanged (7 categories: `minimal_content`, `crawl4ai_error`, `http_error`, `nav_dump`, `cookie_wall`, `login_wall`, `cloudflare`), exported ONLY for `src/crawler/crawl_site.py`'s unattended batch-crawl filter — a different consumer, correctly still automatic. A regression test (`tests/test_scrape_url.py::test_try_scrape_does_not_call_is_garbage_content`) guards against this being called from `try_scrape` again.
- `fit_markdown < 200` chars (`MIN_CONTENT_THRESHOLD`) triggers `raw_markdown` fallback — table-heavy pages filter to near-empty otherwise. This is content SELECTION between two crawl4ai-provided candidates (unchanged by the 2026-08-05 removal), not a garbage/quality verdict — see `meta["fallback_to_raw"]`.
- **`http_status` is a fact, not a verdict, as of 2026-08-05** — a status code no longer gates content on its own. Real evidence both directions: `de.trustpilot.com/review/entega.de` returns HTTP 403 WITH the real 42707-byte review page (a status>=400 gate would have discarded all of it); `idealo.de`'s `OffersOfProduct` page returns HTTP 200 with 401 bytes of "Sorry! Something has gone wrong" (a content classifier let it through as clean).
- **`same_target: true` does NOT prove no redirect happened.** Real CLI run against `idealo.de`'s `OffersOfProduct` page (the motivating case for `is_same_target` itself — see `process-docs/scrape_pipeline/`) came back with `landed_url` IDENTICAL to the requested URL, HTTP 200, the 367-byte "Sorry! Something has gone wrong" block page — `same_target` therefore `true`. The most plausible reading is that the block page is served directly at the requested URL with no browser-level redirect at all, but a redirect BACK to the same URL is equally consistent with this same observation and cannot be distinguished from it using `landed_url` alone — recorded as a candidate explanation, not a settled mechanism. Do not read `same_target: true` + a thin/blocked-looking page as proof the URL was never redirected.
- crawl4ai captures stdout — write debug to files, never `print()`.
- **`crawl4ai_error_message`/`crawl4ai_success`/etc. must be presented as an OBSERVATION, not a verdict, wherever they're surfaced** (log AND, as of 2026-08-05, `_format_scrape_output`'s rendered text) — crawl4ai's own anti-bot detector has documented false positives: `guenstiger.de` reports `"Blocked by anti-bot protection: Cloudflare JS challenge"` from crawl4ai's own detector on a render at `delay_before_return_html=6.0` that returns the full 38691-byte product page (see `_format_scrape_output`'s comment; the render-time question that surfaces the real page is a separate, not-yet-done milestone — untouched here).
- Missing/failed patchright chromium binary looks IDENTICAL to a genuinely empty page unless caught: launch fails in ~300ms with `http_status:null`, `bytes_raw_markdown:null` — exactly the same shape as a blocked/empty scrape. `is_browser_launch_error` guards against this by matching launch-exception substrings (`executable doesn't exist`, `playwright install`, `browsertype.launch`); on match `meta["acquisition_error"]` is `"browser_missing"` (logged at ERROR, not WARNING) with a message naming the fix: `./venv/bin/python -m patchright install chromium`.
- `extract_date`'s `original_date=True` prevents htmldate from preferring a last-modified date WHEN a real publication-date candidate exists, but on a page with NO such candidate (e.g. Sphinx-generated docs with a "Last updated on <date>" footer and no JSON-LD/meta tags) htmldate's extensive-mode cascade can still latch onto that footer text as its only signal — a real, observed false-positive-shaped result, not a bug in this wiring (the code never adds its own guess; it forwards htmldate's own found value, consistent with the library's documented ~90% accuracy). Reference/docs-style pages are a poor domain for this feature in general.
- `PruningContentFilter` WITHOUT `preserve_tags=["pre","code"]` corrupts syntax-highlighted code: `_prune_tree` (crawl4ai's own `content_filter_strategy.py`) recurses into any node it keeps and decomposes children scoring below `threshold`; a highlighter's whitespace-only `<span>` between tokens scores near-zero and gets removed, collapsing `FROM golang:1.22-alpine AS builder` to `FROMgolang:1.22-alpineASbuilder` — confirmed via real CLI scrape of a live dev.to Docker post and the kubernetes.io Service page (crawl4ai issue #2110, open as of 0.9.2, this project's exact version). `preserve_tags` short-circuits `_prune_tree` before it recurses into a matched node, so the WHOLE subtree survives untouched — confirmed on both real repros; `preserve_classes` was evaluated and NOT added, since in both cases the `<pre>` tag itself (not a wrapping div/figure) is what the top-down recursion evaluates directly, so `preserve_tags` alone was sufficient without guessing highlighter-specific wrapper class names (Rouge/Prism/highlight.js all differ). `threshold` stays at 0.48 (empirically calibrated, see `process-docs/scrape_pipeline/scrape_pipeline.md`) — this is a guard on that calibration, not a revision of it. NOT verified against MDN (the third page named in #2110): its interactive code examples never appear in `result.markdown` at all through this scrape path (likely cross-origin `<iframe>` content not captured by `wait_until="load"`) — genuinely untestable here, independent of this fix.
- `avoid_ads` (a `BrowserConfig` param, NOT `CrawlerRunConfig`) is deliberately NOT set. `browser_manager.py`'s `create_browser_context` registers `context.route(pattern, ...abort())` for a fixed, non-configurable list of 21 domain glob patterns (`ad_tracker_patterns`, `browser_manager.py:1302`) — Google Analytics/GTM/doubleclick/Hotjar/Mixpanel/etc. Two decisive negative findings: (1) `etracker.com`/`etracker.de` — the tracker behind this project's own recorded 61s-networkidle cost (`phase_escalation_networkidle_cost_2026-05-24.md`) — are absent from the list; confirmed live on the same BfN.de page, 0/16 requests blocked either way. (2) the glob patterns themselves (`**/google-analytics.com/**`) require a literal `/` immediately before the domain, so they match a bare `https://google-analytics.com/x` but NOT `https://www.google-analytics.com/x` — confirmed with a real Playwright `context.route()` probe (3 URLs, only the bare-domain one triggered the handler); real tracker scripts are served from subdomains almost universally, so this list is largely inert against real traffic even for domains nominally on it. Not revisited unless the list becomes configurable upstream.
- `remove_consent_popups=True` runs `remove_consent_popups.js` on the LIVE page (click "Accept All" across ~100+ CMP-specific selectors incl. CookieYes, then CMP JS APIs, then removes ~140 known CMP container selectors, then CMP iframes, then restores body scroll) BEFORE `page.content()` captures HTML (`async_crawler_strategy.py:1044-1046`, ahead of the capture at line 1085). `excluded_selector` runs LATER, on the captured HTML STRING, inside `content_scraping_strategy.py` — a separate code path, no collision possible; this is a second, complementary layer alongside `excluded_selector` (both act on the live page/HTML BEFORE capture or selection — unaffected by the 2026-08-05 removal of post-hoc content judgment; `strip_consent_prefix`, which acted AFTER capture based on a garbage verdict, is what was removed, not this). Real recovered content on azubiyo.de: `excluded_selector` alone lets ~3400 chars of German CMP banner text through into `raw_markdown`; `remove_consent_popups=True` removes it cleanly (confirmed via real CLI, `bytes_raw_markdown` 41583→37988). Unconditional cost on EVERY page regardless of whether a popup exists: two separate 500ms sleeps — one inside `remove_consent_popups.js` itself (`await new Promise(r => setTimeout(r, 500))`, unconditional "wait for CMP animations" step) and one in Python after the JS eval returns (`page.wait_for_timeout(500)`, `async_crawler_strategy.py:1581`) — measured end-to-end on `rfc-editor.org` (no consent layer): +0.96s wall time (1.93s→2.89s). That same ~1s extra wait also produced a 126-byte `raw_markdown` diff on the RFC page even though no CMP action ever fired there — root-caused (not just observed): the RFC page is a Nuxt.js SPA; a visually-hidden (CSS `clip-rect`, not `display:none`) accessibility `<span>` duplicating the page title finishes client-side hydrating within that extra ~1s window and gets swept into the captured HTML — reproduced identically by adding `delay_before_return_html=1.1` alone with `remove_consent_popups=False`, proving it's a generic "waited longer before capture on a still-hydrating page" artifact, not a DOM mutation from the consent-removal JS itself. One 60.32s timeout with zero content was observed once against `stepstone.de` with this switch on; NOT reproduced across 3 immediate retries (including the exact production config) — logged as an unresolved, non-reproduced anomaly, not blocking. `avoid_ads` was rejected on the same investigation pass — see above. With `remove_consent_popups=True` (current default) and the now-explicit `delay_before_return_html=2.0`, a differential CLI run on rfc-editor.org (`delay_before_return_html` 0.1 vs 2.0, both otherwise identical) showed IDENTICAL `bytes_raw_markdown` (11218 both) — the consent-popup's own forced ~1s wait already crosses this page's hydration window even at the 0.1s library default, so rfc-editor.org does not exercise `delay_before_return_html` under the current full config; it remains valid evidence only that raising it to 2.0 causes no regression here, not that the 2.0s wait does observable work on this specific page.
